# Хранилище конфиденциальных данных SecuRawr

## Назначение

Хранилище предназначено для безопасного хранения файлов данных:
* Произвольные файлы данных;
* Текстовые файлы;
* Логины/пароли;
* Данные кредитных карт.

## Шифрование данных

### 1. Архитектура: Разделение ключей (KDF)
Для шифрования данных будет использован отдельный хеш, не совпадающий с хешем для входа (аутентификации) пользователя. Из одного пароля создаётся два разных ключа. Для этого сервер должен хранить и отдавать клиенту две разные соли.

* **Auth Key:** Вычисляется на клиенте. Отправляется на сервер для аутентификации (вместо пароля).
* **Master Key:** Вычисляется на клиенте. Никогда не покидает клиентское устройство. Используется для шифрования файлов.

**Формула вычисления на клиенте:**
> `Master_Key = Argon2id(Password, Encryption_Salt, params)`

### 2. Envelope Encryption (Конвертное шифрование)
Шифровать сами файлы напрямую `Master_Key` непрактично, так как при смене пароля пришлось бы перешифровывать большие объёмы данных, поэтому будет использоваться подход, напоминающий матрёшку:

* **DEK (Data Encryption Key):** Для каждого файла CLI-клиент генерирует случайный криптостойкий ключ (например, 32 байта для AES-256).
* **Шифрование данных:** CLI-клиент шифрует файл данных этим `DEK`.
* **Шифрование ключа:** Сам `DEK` зашифровывается с помощью `Master_Key`.
* **Хранение:** На сервер (и в кеш) уходит пакет: `[Encrypted DEK] + [Encrypted Data]`.

**Плюс для мобильности:** Чтобы получить доступ к файлам на новом ПК, CLI-клиенту достаточно скачать `Encryption_Salt`, вычислить `Master_Key` и расшифровать маленькие блоки `DEK`.

### 3. Выбор инструментов в Go
В экосистеме Go будут применены современные и быстрые стандарты:

* **KDF (Генерация ключей):** пакет `golang.org/x/crypto/argon2`. Используем именно `Argon2id`, так как он защищен от атак по побочным каналам и эффективен против GPU.
* **Шифрование (AEAD):** пакет `crypto/aes` в режиме `GCM`, который на большинстве современных x86 процессоров ускоряется аппаратно (AES-NI).

### 4. Процесс работы CLI-клиента

**Регистрация:**
1. Клиент запрашивает у сервера генерацию двух солей: `Auth_Salt` и `Encryption_Salt`.
2. Сервер сохраняет их в БД.
3. Клиент вычисляет `Auth_Key` (для регистрации) и `Master_Key` (для первого шифрования файлов).
4. Все файлы шифруются уникальными `DEK`, которые «запираются» на `Master_Key`.

**Офлайн-доступ и восстановление:**
* **При входе:** CLI скачивает с сервера `Encryption_Salt` (и сохраняет в локальный конфиг для работы без сети).
* **Ввод пароля:** Пользователь вводит пароль, CLI восстанавливает `Master_Key`.
* **Кеш:** Для файлов в локальном кеше CLI берет `Encrypted_DEK`, расшифровывает его своим `Master_Key` и получает доступ к данным.
* **Связь с сервером не нужна**, пока у нас есть локальная копия соли и зашифрованных файлов.

### 5. Безопасность локального хранения
Чтобы не заставлять пользователя вводить пароль при каждой команде (например, `securawr list` или `securawr get`), `Master_Key` нужно где-то хранить временно.

**Рекомендуемый путь:** Библиотека `github.com/99designs/keyring`. Она позволяет сохранить `Master_Key` в системном хранилище ОС (Apple Keychain, Windows Credential Manager или Linux Secret Service/KWallet). Это гораздо безопаснее, чем хранить ключ в текстовом конфиге или переменной окружения.

## Резюме по стеку

| Компонент | Технология |
| :--- | :--- |
| KDF | Argon2id (соль берется из БД сервера) |
| Шифрование файлов | AES-256-GCM (Envelope Encryption) |
| Хранение метаданных | БД сервера (соли, зашифрованные `DEK`, параметры Argon2) |
| Локальные секреты | keyring (библиотека для доступа к Keychain ОС) |
| Передача данных | HTTPS (TLS 1.3) |

**Конфигурация Argon2id:**
* **Memory (m):** 65536 (64 MB)
* **Iterations (t):** 3
* **Parallelism (p):** 4
* **Salt length:** 16 bytes

Такая схема защищает файлы даже при полном взломе базы данных (так как у хакера нет пароля пользователя для вычисления `Master_Key`), но при этом позволяет пользователю не бояться поломки ноутбука.

## Хранение секретов

| Секрет | Из чего и где генерируется | В какой момент | Где хранится | В каком виде |
| :--- | :--- | :--- | :--- | :--- |
| Пароль | Вводит пользователь на Клиенте | Регистрация / Вход | Нигде (только в RAM) | Открытый (ввод) |
| Auth_Salt | Крипто-рандом на Сервере | Регистрация | БД Сервера | Открытый |
| Auth_Key | `Argon2id(Password + Auth_Salt)` на Клиенте | Вход (каждый раз) | Нигде (передается на сервер) | Хеш |
| Auth_Hash | `Argon2id(Auth_Key + Pepper)` на Сервере | Регистрация / Вход | БД Сервера | Хеш |
| Encrypt_Salt | Крипто-рандом на Сервере | Регистрация | БД Сервера | Открытый |
| Master_Key | `Argon2id(Password + Encrypt_Salt)` на Клиенте | Вход / Шифрование | RAM Клиента / Keyring | Хеш (Ключ) |
| DEK (ключ файла) | Крипто-рандом на Клиенте | Создание файла | В метаданных файла | Зашифрован (`Master_Key`) |
| Server_Pepper | Статическая строка в конфиге Сервера | Деплой проекта | Файлы конфига / ENV | Открытый (секрет) |

## Работа с данными пользователей

Процедура регистрации с использованием перца выглядит линейно: клиент доверяет серверу доставку сырого пароля, а сервер берет на себя всю ответственность за его безопасное превращение в хеш.

### 1. Безопасная передача (HTTPS)
Безопасность канала обеспечивается протоколом HTTPS (TLS). Внутри защищенного канала передается не пароль, а предварительно вычисленный `Auth_Key`.

### 2. Алгоритм регистрации на сервере
Когда сервер получает POST-запрос с логином и паролем, происходит следующее:

1. **Генерация солей:** Сервер генерирует случайные `Auth_Salt` и `Encryption_Salt`.
2. **Отправка соли:** Сервер отправляет `Auth_Salt` клиенту.
3. **Вычисление на клиенте:** Клиент берет пароль и соль, считает `Auth_Key` и отправляет его серверу.
   > На клиенте: `Auth_Key = Argon2id(Password, Auth_Salt)`
4. **Получение перца:** Сервер считывает секретный `Server_Pepper` из своих защищенных переменных окружения.
5. **Замешивание и Хеширование:** Сервер объединяет полученный от клиента ключ с перцем и хеширует.
   > На сервере: `Auth_Hash = Argon2id(Auth_Key, Server_Pepper)`
6. **Запись в базу данных:** Сервер сохраняет в таблицу `users`:
   * `login`
   * `Auth_Salt`
   * `Encryption_Salt`
   * `Auth_Hash` (результат работы Argon2 на сервере)
   * *Сами `Server_Pepper` и `Auth_Key` в базу не записываются.*

**Пример структуры данных в БД:**

| id | login | salt | password_hash (Argon2) |
| :--- | :--- | :--- | :--- |
| 1 | user_alpha | 8f2a... | `$argon2id$v=19$m=65536,t=3,p=4$c29s...` |

### Что если перец нужно изменить? (Rotation)
Иногда компании хотят менять перец раз в год. Для этого используется **версионность**:
* В базе рядом с хешем хранится номер версии перца (например, `v1`).
* Если сервер видит, что у пользователя `v1`, а сейчас актуален `v2`, он после успешного входа тихонько пересчитывает хеш с новым перцем и обновляет запись в базе.
